# 요구사항 정의서 — 대용량 블로그 알림 시스템

> 원본 요구사항(기능/비기능)을 실제 구현 단위로 분해한 문서. 각 항목은 이후 설계 문서 및 구현 태스크의 기준선(baseline) 역할을 한다.

## 0. 배경 요구사항 (원문)

**기능적 요구사항**
- 인기 작가가 글을 등록하면 구독한 10만 명에게 Push 알림 발송
- 사용자는 웹/앱에서 실시간 알림 목록을 확인하고 읽음 처리
- 개별 구독자의 알림 수신 설정(Push/Email/Mute) 반영

**비기능적 요구사항**
- Low Latency: 글 작성 후 5초 이내 전체 알림 발송 완료
- High Availability: 알림 서버 장애 시에도 블로그 작성 기능 정상 작동
- Scalability: 순간적인 10만 QPS 이상의 트래픽 흡수

## 1. 기능 요구사항 (Functional Requirements)

### FR-1. 구독(Subscription) 관리
- FR-1.1 사용자는 작가를 구독/구독 취소할 수 있다.
- FR-1.2 작가별 구독자 목록을 조회할 수 있다 (내부 시스템용, 페이지네이션 필수 — 10만 건 단위 조회 가정).
- FR-1.3 구독 정보는 별도 저장소에 보관하며, 알림 발송 시 스냅샷 형태로 조회한다 (발송 도중 구독 변경이 발송 중인 배치에 영향을 주지 않음).

### FR-2. 알림 발송 트리거 (Publish → Fan-out)
- FR-2.1 작가가 글을 등록(Publish)하면 이벤트가 발행된다 (`PostPublished` 이벤트).
- FR-2.2 이벤트 발행은 블로그 글 등록 트랜잭션과 분리되어야 한다 (Outbox 패턴 등으로 발행 실패가 글 등록을 막지 않도록).
- FR-2.3 이벤트 컨슈머는 구독자 목록을 조회하여 개별 알림 메시지로 팬아웃(Fan-out)한다.
- FR-2.4 팬아웃은 배치/청크 단위로 처리하여 10만 명 규모에서도 안정적으로 동작해야 한다.
- FR-2.5 동일 이벤트에 대한 중복 발송을 방지한다 (멱등성 보장 — 이벤트 ID/구독자 ID 조합 기준).

### FR-3. 알림 수신 설정 반영
- FR-3.1 사용자는 알림 수신 채널을 Push / Email / Mute 중에서 선택할 수 있다.
- FR-3.2 설정은 전역 단위(모든 작가에 공통 적용)로 지정한다. 특정 작가에 대해서만 알림을 원치 않는 경우는 별도의 작가별 설정이 아니라 **해당 작가 구독 취소**로 처리한다 (`domain-design.md` §6 참고 — 구독 여부와 전역 채널 설정 두 가지만으로 발송 대상을 결정).
- FR-3.3 팬아웃 시점에 ①구독 여부 ②전역 수신 설정을 조회하여 Mute이거나 구독하지 않은 대상은 발송 대상에서 제외한다.
- FR-3.4 채널별 발송기(Push/Email)는 독립적으로 동작하며 하나의 장애가 다른 채널에 영향을 주지 않는다.

### FR-4. 알림 발송 (Delivery)
- FR-4.1 Push 알림은 외부 Push 서버(별도 시스템으로 가정 — FCM/APNs 연동 자체는 그 서버의 책임)에게 발송을 위임한다. 이 시스템의 책임은 `DeliveryAttempt` 생성과 그 Push 서버로의 요청 전달까지다.
- FR-4.3 발송 실패 시 재시도 정책(exponential backoff, 최대 재시도 횟수)을 적용한다.
- FR-4.4 재시도 초과 시 실패 큐(DLQ)에 적재하고 별도 모니터링 대상으로 관리한다.

### FR-5. 알림 조회 및 읽음 처리 (In-app Notification)
- FR-5.2 사용자는 개별 알림 또는 전체 알림을 읽음 처리할 수 있다. **(구현 대상 — 유일하게 남는 조회/조작 API)**

### FR-6. 작가 글 작성 (지원 기능)
- FR-6.1 작가는 글을 작성/등록할 수 있다 (알림 시스템의 트리거 소스로서 최소 기능만 구현).
- FR-6.2 글 등록 API는 알림 시스템의 가용성과 무관하게 항상 응답 가능해야 한다 (NFR-2와 연결).

## 2. 비기능 요구사항 (Non-Functional Requirements)

### NFR-1. Low Latency
- NFR-1.1 글 등록 시점부터 10만 명 전원에 대한 알림 발송(발송 큐 적재 완료 기준)까지 5초 이내 완료.
- NFR-1.2 "발송 완료"의 정의를 명확히 함: 알림 레코드 생성 + 발송 큐 적재까지를 SLA 기준으로 삼고, 외부 Push/Email 게이트웨이의 실제 전달(delivery)은 Best-effort 비동기로 분리.
- NFR-1.3 팬아웃 처리량 목표: 100,000건 / 5초 이상 = 최소 20,000 msg/sec 처리 가능한 워커 구조.
- NFR-1.4 성능 측정을 위한 부하 테스트 시나리오 및 결과를 문서화한다 (k6/Locust 등 활용).

### NFR-2. High Availability
- NFR-2.1 알림 시스템(팬아웃 워커, 발송기, 큐)의 장애가 블로그 글 등록(Write Path)에 영향을 주지 않는다.
- NFR-2.2 이벤트 발행은 Outbox 패턴 + 별도 Relay 프로세스로 분리하여, 메시지 브로커 장애 시에도 글 등록 트랜잭션은 정상 커밋된다.
- NFR-2.3 알림 조회(Read Path)는 발송 파이프라인과 분리된 저장소/캐시를 사용하여 장애 영향을 최소화한다.
- NFR-2.4 장애 주입 테스트(Chaos test) 시나리오를 최소 1개 이상 구현/문서화한다 (예: 알림 워커 강제 종료 후 글 등록 API 정상 동작 확인).

### NFR-3. Scalability
- NFR-3.1 순간 10만 QPS 이상 트래픽(팬아웃으로 생성되는 발송 요청 기준)을 흡수할 수 있는 메시지 큐/브로커 구조를 사용한다.
- NFR-3.2 팬아웃 워커와 발송기(Sender)는 수평 확장(Horizontal Scaling) 가능한 구조로 설계한다 (Stateless, Consumer Group 기반).
- NFR-3.3 특정 인기 작가에 대한 트래픽 쏠림(Hot Partition)을 고려한 파티셔닝 전략을 수립한다.
- NFR-3.4 백프레셔(Backpressure) 및 Rate Limiting 정책을 통해 다운스트림(Push/Email 게이트웨이) 과부하를 방지한다.

### NFR-4. 기타 (설계 완성도를 위한 보강 항목)
- NFR-4.2 멱등성 및 정확히-한번(at-least-once + dedup) 전달 보장 전략을 문서화.
- NFR-4.3 데이터 정합성: 읽음 처리 등 사용자 액션이 동시성 상황에서도 일관되게 반영.

## 3. 범위(Scope) 정의

### In Scope (구현 대상)
- 구독 관리 API
- 글 등록 → 이벤트 발행 (Outbox) → 팬아웃 → 발송 파이프라인 전체
- 알림 수신 설정(Push/Email/Mute) API
- 알림 읽음 처리 API (개별/전체) — 목록 조회는 제외, 읽음 처리만
- 부하 테스트 및 장애 주입 테스트, 결과 문서화
- 기본 로깅 (구조화된 애플리케이션 로그 수준)

### Out of Scope (목업/생략 대상, README에 명시)
- 실제 FCM/APNs 연동 — 별도의 외부 Push 서버가 있다고 가정하고, 이 시스템은 그 서버로 발송을 위임(요청)하는 지점까지만 구현한다.
- 작가/글 CRUD의 풀 기능(에디터, 미디어 업로드 등) — 알림 트리거용 최소 API만 구현
